## Canonical engineering graph

Canonical identities are `KepwarePath`, `SUP_<uuid>`, Supplier-owned `CNT_<uuid>`, `EPT_<uuid>`, and stable `ResourceId`. Absolute filesystem paths are not cross-module identities.

```text
KepwarePath -> EPT_ -> SUP_
EPT_ -> MAN_
EPT_ -> DWG_
EPT_ -> QUO_

SUP_ -> QUO_
KepwarePath -> ResourceId
```

Direct Tag-to-Resource links remain backward compatible. Tag relationships use `references.json`. Resource-to-Resource engineering relationships use `relationships.json`.

## Supplier and Contact state

Supplier Profiles support optional string-valued `tax_id`. Leading zeroes and stored formatting are preserved; normalization is used only for matching. Tax ID is the strongest planned quotation Supplier signal. Matching never auto-merges and multiple candidates may remain ambiguous.

Contacts remain stable `CNT_` identities owned inside their Supplier profiles. No independent Contact registry was introduced.

## Approved APIs

Read-only candidate APIs:

- `GET /api/suppliers/candidates`
- `GET /api/contacts/candidates`
- `GET /api/equipment-parts/candidates`
- `GET /api/suppliers/{resource_id}/equipment-parts`

They return stable canonical IDs, canonical metadata, and match evidence. They never auto-select, create, update, merge, or create relationships.

Relationship APIs:

- `GET /api/resource-relationships/{source_resource_id}`
- `POST /api/resource-relationships/link`
- `POST /api/resource-relationships/unlink`

Relationship mutations remain protected by `KM_RESOURCE_WRITE_ENABLED` and require an explicit confirmed write operation.
